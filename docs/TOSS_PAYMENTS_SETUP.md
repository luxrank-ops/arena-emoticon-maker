# 토스페이먼츠 결제 연동 설정 및 출시 전 점검

## 현재 범위
- 토스 주문서형 SDK v2와 서버 승인 API는 **일회성 크레딧 상품**에 연결한다. 플랜 정기결제, 굿즈 결제, 가상계좌, 결제 취소·환불 API와 웹훅은 구현하지 않았다. 구독과 운영 굿즈 주문은 차단한다.
- 실제 서비스 제공 전, 환불·청약철회 정책, 통신판매업 정보, 사업자 주소 및 고객센터 운영 절차, 상품과 가격·제공 조건을 확정하고 법률 검토한다.
- 주문 생성, 동의 저장과 승인 후 원장 반영은 원격 CAS 저장소를 필수로 사용하고, 실패할 때 로컬·메모리 폴백을 금지한다. 결제 승인 응답을 받지 못하거나 저장이 실패하면 동일 주문·결제키로 다시 확인한다. 결제 승인과 원장 반영은 별도 시스템이므로 고객센터의 미지급 주문 대조 및 복구 절차가 필요하다.
- 결제 UI의 카드 기반 선택만 허용한다. 토스 상점관리자의 결제 UI에서도 카드 기반 결제 외 수단(특히 가상계좌, 브랜드페이, 커스텀 결제)을 비활성화한다. 미지원 수단의 입금·취소 웹훅은 처리하지 않는다.

## 설정
1. 토스페이먼츠 가입·심사 후 주문서형 결제의 **서로 맞는** 클라이언트 키와 시크릿 키를 발급받는다. 시크릿 키는 절대 클라이언트·Git·대화에 넣지 않는다.
2. 개발 환경에서 `PAYMENT_PROVIDER=toss`, `NEXT_PUBLIC_TOSS_CLIENT_KEY` 및 서버 전용 `TOSS_SECRET_KEY`에 같은 상점의 테스트 키를 안전하게 설정한다. 실제 승인을 테스트하려면 토스 테스트 환경을 사용한다. `mock`은 로컬 개발 전용이다.
3. 운영 환경에서는 테스트 키, mock, 미설정 키 또는 서로 다른 종류의 키를 거부한다. 배포 환경에 영속적인 Firestore 또는 KV CAS 저장소를 설정하고, 토스 결제 UI의 수단·도메인 및 콜백 동작을 확인한다.
4. 실제 운영 활성화 전에 라이브 키를 배포 플랫폼의 안전한 환경변수에 직접 등록하고 `PAYMENT_PROVIDER=toss`로 설정해 재배포한다. 키 종류가 같아도 동일 상점에서 발급된 쌍인지 서버가 알 수 없으므로 실제 테스트와 계약 정보를 확인한다. 섣불리 활성화하지 않는다.

## 로컬 모의 검증
- `scripts/test-checkout.mjs`는 실제 토스 API가 아닌 `scripts/toss-test-stub.cjs`와 격리된 데이터 저장소가 있는 로컬 서버에서만 실행한다. 실제 인증·결제창 테스트를 대체하지 않는다.
- 예: 로컬 개발 서버에 `CHECKOUT_TEST_STUB=1`, `NODE_OPTIONS=--require ./scripts/toss-test-stub.cjs`, `PAYMENT_PROVIDER=toss`, `NEXT_PUBLIC_TOSS_CLIENT_KEY=test_ck_dummy`, `TOSS_SECRET_KEY=test_sk_dummy` 및 격리된 `DATA_DIR`을 설정한 뒤, 별도 터미널에서 `CHECKOUT_TEST_BASE_URL=http://127.0.0.1:3000 CHECKOUT_TEST_STUB=1 node scripts/test-checkout.mjs`를 실행한다. 스텁과 가짜 키는 배포하지 않는다.

## 출시 전 필수 QA
- 실제 토스 테스트 키로 PC·모바일 브라우저에서 결제창, 동의, 인증 성공·실패·취소, 중복 클릭, 새로고침, 금액 변조, 승인 실패와 복구를 검증한다. 테스트 키는 운영 모드에서 차단되므로 별도 격리 개발 환경에서 진행한다.
- 원격 저장소 장애, 타임아웃, 승인 성공 후 데이터 저장 실패·재시도, 동시 승인 요청 시 중복 크레딧 방지를 테스트하고 운영자가 결제 조회를 대조하는 절차를 마련한다.
- 현재 결제 완료 페이지는 같은 브라우저 탭에서 재시도를 지원한다. 탭을 닫거나 세션이 바뀐 경우 고객센터에서 주문번호와 토스 거래를 대조해야 한다. 자동 정기결제·환불·굿즈 주문과 가상계좌 입금은 지원하지 않는다.
