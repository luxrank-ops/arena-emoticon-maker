# 결제 운영·대사·비상 대응

> 적용 범위: 토스 주문서형 결제의 **일회성 크레딧 상품**. 정기결제·가상계좌·자동 환불·굿즈 판매는 활성화 범위가 아니다.

## 1. 출시 전 go / no-go

아래를 모두 확인하기 전에는 라이브 키로 전환하지 않는다.

- `npm run test:payments`, 격리된 토스 스텁 서버의 `npm run test:checkout` 및 재시작 후 `npm run test:checkout:suspended` 통과
- `npm run preflight:payments` 통과 후, 출력되는 수동 항목까지 사람이 확인
- 토스 상점 심사·계약, 실제 도메인과 카드 기반 결제 외 수단 비활성화
- 같은 상점의 라이브 클라이언트·시크릿 키를 배포 Secret에 등록
- Firestore 또는 KV CAS 연결과 장애 시 fail-closed 확인
- 사업자·통신판매·고객센터 정보와 환불정책 법률 검토·시행일 확정
- 실제 토스 테스트 키로 PC·모바일 결제, 취소, 인증 실패, 새로고침, 중복 클릭 검증
- 아래 미지급 복구와 환불 접수 절차를 운영 담당자가 실제로 연습

preflight는 값의 형식과 누락을 검사할 뿐 실제 계약·연결·법무·결제 성공을 보장하지 않는다.

## 2. 일상 대사

1. 운영 콘솔 `/admin`의 **결제 대사 점검**을 확인한다.
2. `승인 시도 후 미지급`은 결제키가 저장됐지만 주문이 아직 `PENDING`인 상태다. 방금 시작한 주문은 진행 중일 수 있으므로 잠시 기다린다.
3. 토스 상점관리자에서 주문번호·금액·결제 상태를 대조한다.
4. 토스 상태가 `DONE`이고 주문 소유자가 확인되면 **토스 승인 결과로 복구**를 실행한다. 서버는 저장된 결제키를 다시 승인·조회하고, 검증된 주문만 한 번 지급한다.
5. `PAID 주문과 크레딧 원장 불일치`는 자동 복구하지 않는다. 새 결제를 일시 중단하고 토스 거래·주문·원장을 수동 대조한다.
6. 일별 결제 금액과 크레딧 구매 원장을 대조하고, 처리자·확인 시각·조치 내역을 운영 기록에 남긴다.

관리자 목록과 API에는 결제키를 표시하지 않는다. 고객에게 카드 번호·비밀번호·시크릿 키를 요청하지 않는다.

## 3. 고객이 직접 복구하는 방법

- 결제 성공 페이지에서 승인 확인이 실패하면 **승인 결과 다시 확인**을 누른다.
- 페이지를 닫았거나 성공 URL 정보가 사라지면 `/billing`의 해당 주문에서 **승인 결과 확인**을 누른다.
- 아직 결제창을 제출하지 않은 주문은 **결제 계속**만 표시되며 복구 요청으로 지급되지 않는다.
- 다른 계정·다른 게스트 세션의 주문은 소유권 검증 때문에 복구되지 않는다. 고객센터가 주문번호와 토스 거래를 대조한 뒤 관리자 복구를 사용한다.

## 4. 장애별 대응

| 상황 | 대응 |
|---|---|
| 승인 응답 손실·타임아웃 | 새 결제를 다시 하지 않고 같은 주문의 승인 결과를 확인한다. 서버는 주문 단위 멱등키와 결제키 조회를 사용한다. |
| 토스는 `DONE`, 남은 주문은 `PENDING` | 운영 콘솔에서 소유자·금액을 대조한 뒤 복구한다. |
| `PAID`인데 구매 원장이 없거나 중복 | 자동 지급·DB 직접 수정을 하지 않고 새 결제를 중단한 뒤 수동 대조한다. |
| 저장소 `STORE_BUSY` | 저장소 장애를 우회해 로컬에 기록하지 않는다. 저장소를 복구하고 같은 주문을 재시도한다. |
| 승인 금액·주문번호·결제수단·상태 불일치 | 지급하지 않고 `PAYMENT_REVIEW`로 남긴다. 토스 거래와 대조한다. |
| 고객이 중복 결제를 주장 | 두 주문번호와 토스 결제키를 대조한다. 크레딧을 임의로 더 지급하지 않고 확정된 환불 절차를 적용한다. |

## 5. 새 결제만 멈추는 비상 스위치

배포 환경변수에 `PAYMENT_CHECKOUT_DISABLED=1`을 설정하고 재배포한다.

- 중단: 새 주문 생성과 결제 준비
- 계속 허용: 기존 주문의 승인 확인, 사용자·관리자 복구, 결제 내역 조회

원인 조치와 미지급 주문 대사가 끝나면 `0`으로 되돌린다. `PAYMENT_PROVIDER=mock`으로 바꾸거나 키를 삭제하면 기존 주문 복구까지 막히므로, 미지급 건이 남은 비상 상황에서는 사용하지 않는다.

## 6. 환불 접수

현재 자동 결제 취소·부분 환불과 크레딧 소비 귀속은 구현되지 않았다. 자동 환불 버튼을 임의로 추가해 실제 취소와 원장이 어긋나게 하지 않는다.

1. 주문번호, 결제일, 요청 사유, 사용 여부를 접수한다.
2. 확정된 `/refund` 정책과 법령에 따라 토스 상점관리자에서 취소 가능 금액을 확인한다.
3. 토스 취소 결과와 남은 크레딧·생성 결과를 대조해 승인된 조치를 기록한다.
4. 고객에게 처리 결과와 예상 환급 시점을 안내한다.
5. 자동 환불을 도입할 때는 취소 API, 전액·부분 취소, 원장 역분개, 크레딧의 유상·무상 소비 귀속, 중복 요청과 웹훅을 별도 설계·검토한다.

## 7. 정기 점검

- CI `Payment readiness` 워크플로의 단위·통합 테스트 확인
- 결제 대사 0건 확인과 미해결 건의 책임자·기한 기록
- Secret 접근 권한과 로그에 키·카드 정보가 없는지 점검
- 고객센터 실제 접수 테스트와 환불정책 변경 여부 검토
- 구독·가상계좌·굿즈가 계속 차단되어 있는지 확인
